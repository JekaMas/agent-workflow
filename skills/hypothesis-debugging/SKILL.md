# Hypothesis debugging

Use after one direct attempt fails or when the failure owner is unknown. Size the evidence record to the problem; a compact record is sufficient for a simple case. Work inside the selected change and user authority: diagnosis-only scope reports findings; authorized implementation continues through repair and revalidation. No new role or task list.

1. Separate observed discrepancies from theories: expected/actual behavior, impact, source state, time window and evidence. Classify implementation, oracle/specification, harness/environment and unresolved failures separately.
2. Inspect existing artifacts before choosing a rerun. Every discrepancy needs at least one falsifiable hypothesis; each hypothesis must map to the discrepancies it explains. Missing coverage calls for more investigation before a speculative patch or broad rerun. Each hypothesis names a concrete mechanism, supporting evidence, a discriminating predicted signal, a contradicting signal, and the owner if true. Weak/unfalsifiable explanations are research notes, not justification for a speculative fix.
3. Choose the smallest authorized experiment that distinguishes plausible causes. Prefer existing raw evidence or a focused test over expensive external/full-stack work. Consider services crossed, uncontrolled inputs and opaque boundaries. Independent checks may run together when authorized and resource-safe; no mandatory parallel wave or fixed attempt count.
4. Classify confirmed, refuted, partial, inconclusive or blocked. Retain material hypotheses, experiments, actual results, evidence links, dispositions and revisit conditions in the existing change record. A passing retry does not erase an intermittent failure. Refuted ideas leave the active set but remain recoverable.
5. For each proposed correction, require a confirmed hypothesis, exact owner, expected code change, approval risk and planned proving tests. Identify the discriminator and evidence confirming that cause. Do not bundle an unconfirmed cause into a patch. Independent confirmed causes may share a batch only when each retains its own owner, discriminator, proving test and rollback boundary. Preserve paired positive/negative and relevant ordering cases. Compilation/setup failure is not behavioral reproduction; explain unavailable pre-fix evidence without weakening acceptance.
6. Repair within existing authority, rerun affected checks and inspect the result. Continue useful work, replan when evidence changes the approach, and ask only for a material decision or missing authority after independent work. Preserve initial failures and regressions. Do not hide a blocked criterion behind a debug report or repeat an unchanged failed approach.

For classification/lifecycle bugs, enumerate required outcomes and facts observable at decision time. Pair cases across delayed activation, owner replacement, restart and pruning where relevant. If two required outcomes have identical permitted observations, retain that concrete impossibility witness and identify the missing durable fact or contract decision; a heuristic cannot establish the requested distinction.

Use `references/evidence-sources.md` for source selection and costly-run decisions. For explicit handoffs only, use `assets/handoff.md`. Preserve unrelated work and active run evidence. Diagnosis does not grant production access, destructive setup changes, deployment or delegation. For repeated failures, check whether the relevant instruction was present, loaded, followed and capable of distinguishing the failure. Do not misclassify an instruction or routing defect as another production hypothesis. Record the finding in the current change; compare workflow effectiveness only when requested. If the same signature recurs after an approved workflow experiment, mark it ineffective and recommend reverting or replacing it instead of adding another clause. Reusable workflow changes still require task authority; do not promote speculative causes into permanent instructions.
